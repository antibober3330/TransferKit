# Правила роботи над TransferKit

Цей файл є коротким кореневим довідником для розробників і Codex. Канонічні продуктні вимоги — у `PROJECT_SPEC.md`; поточні рішення, контракти та прогрес — у `docs/project/DECISIONS.md`, `shared/CONTRACTS.md` і `WORK_CHECKLIST.md`.

## Реалізація

- Насамперед використовувати офіційні Android API й документовані дозволи.
- Не реалізовувати root, `su`, exploit-и, Magisk-модулі, kernel modules або інший обхід sandbox.
- Capability probe має бути read-only: жодних записів, перезавантаження, зміни налаштувань або збору повного `getprop`.
- Capability визначати під час виконання на кожному пристрої. Показувати метод, потрібні дозволи, fallback і конкретну причину недоступності.
- `FAILED_INTEGRITY` — окрема помилка. SHA-256 mismatch ніколи не агрегується як `PARTIAL` чи `OK`.
- `OK` означає фактичний restore та post-verification, не лише прийом даних.
- Після resume не позначати передачу успішною без повторної post-verification. `FAILED_INTEGRITY` є непереборним і не може бути зведений до `OK` чи `PARTIAL`.
- Streaming restore має ті самі SHA-256 перед restore та post-verification гарантії, що й batch; не називати його менш цілісним. У UI пояснювати, що при обриві всередині item streaming перекачує цей item з початку.
- Android SDK API не є доказом OEM сумісності. OEM adapter лише додає capability/evidence/quirks і не переносить дані.

## Дані та безпека

- Перед restore вимагати явне підтвердження; встановлення кожного APK підтверджується окремо.
- Не журналювати вміст файлів, паролі, токени, QR секрети, координати чи повні системні дампи.
- Тимчасові дані видаляти після завершення; перервану передачу відновлювати лише з підтверджених чекпойнтів.
- Перед Space Preflight автоматично зіставляти вибрані items із target inventory. Точний duplicate пропускати лише за повного scan coverage та збігу категорії, розміру і SHA-256; не вимагати від користувача ручного пошуку/рішення по кожному duplicate. Near-duplicate фото класифікувати локально за перевіреною політикою; неоднозначні кадри автоматично зберігати в TransferKit collection, не відкидати й не блокувати transfer.
- Не видаляти файли користувача автоматично. Очищати можна лише власний TransferKit staging після явного підтвердження й показу точного обсягу; активні checkpoints залишати без змін.
- Wi-Fi transport використовує TLS 1.3; токен pairing одноразовий і не потрапляє до логів.
- Недоступні категорії описувати чесно до перенесення; не імітувати можливості Smart Switch чи системних підписаних застосунків.
- Recovery identity формується з installation-scoped public key TransferKit; не використовувати IMEI/serial або Android build fingerprint для peer identity. Private key зберігається в Android Keystore й не експортується; якщо ключ недоступний після reinstall, старий resume блокується та потребує нового transfer. Peer має підписати свіжий challenge — одного заявленого fingerprint недостатньо.

## Контракти й зміни

- Джерело істини для машинних значень — `shared/CONTRACTS.md`; для wire format — `shared/protocol.md` і JSON Schemas у `shared/`.
- Перед зміною формату оновлювати Python/Kotlin моделі, schema, приклади в `PROJECT_SPEC.md` і regression тести.
- Кожну зміну записувати append-only у `docs/project/DEVELOPMENT_LOG.md` з дев’ятьма полями, визначеними у `DECISIONS.md`.
- Активно вести кореневий реєстр `що варто добавити з поясненням чому.txt`: оцінювати нові ідеї/прогалини за доказом і поточними файлами; для кожної фіксувати дату, причину та доказ, очікувану користь, залежності/ризики, оцінку можливості й стан. Оновлювати запис, коли змінюється рішення; реєстр є backlog пропозицій, не джерелом прийнятих вимог.
- Виконувати пункти `WORK_CHECKLIST.md` послідовно; позначати зробленим лише те, що перевірено. Зовнішні апаратні залежності залишати явно частковими.

## Перевірки

- Python unit tests: `python -m unittest discover -s tests -v`.
- Android build/test: використовувати SDK/Gradle лише коли локальне середовище готове; не заявляти про фізичний acceptance без реальних пристроїв.
- Перед фінальним звітом запускати релевантні тести після змін контрактів і коду.
