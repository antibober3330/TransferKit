# Рішення щодо реалізації TransferKit

Цей файл фіксує робочі рішення там, де ТЗ залишає відкритий вибір або має внутрішню неузгодженість. Канонічні припущення не розширюють дозволені можливості Android і не приховують недоступність категорій.

| ID | Рішення | Підстава | Наслідок |
|---|---|---|---|
| D-001 | Взяти за основу §3.3: Android 8.0 / minSdk 26, без root, Shizuku опційний, sideload. | У §3.3 це прямо визначено як default до отримання інших рішень. | Усі категорії мають показувати runtime-доступність; недоступність дозволу не маскується. |
| D-002 | Виконувати роботи поетапно M1→M5. M1 лишається вузьким технічним етапом A+B; цільовий обсяг першого продуктового MVP — A+B+D+E згідно §3.3. | §3.3 і опис M1 суперечать одне одному щодо слова «MVP». Збережено обидва наміри як релізний обсяг і ранній milestone. | D/E реалізовувати після стабільного ядра A+B, а критерій готовності M1 не розширювати без потреби. |
| D-003 | Не вважати планувальну доступність доказом успішного перенесення. Звітувати окремо capability, передано, перевірено та відновлено. | Наскрізні етапи §5 і формат звіту §8 вимагають окремих лічильників і причин. | `OK` дозволений лише після фактичного restore та post-verification. |
| D-004 | Використовувати сталі машинні ID категорій: `photos`, `videos`, `audio`, `documents`, `downloads`, `contacts`, `calendar`, `sms`, `call_log`, `apks`, `settings`, `app_data`, `wifi_passwords`, `launcher_layout`, `accounts`, `drm`, `banking_apps`, `two_factor_tokens`. | ТЗ наводить змішані агреговані й деталізовані назви. | Tier та тип даних визначаються контрактом; не об’єднувати різні результати під одним статусом. |
| D-005 | `FAILED_INTEGRITY` є станом категорії/елемента з найвищим пріоритетом; жодне агрегування не може понизити його до `PARTIAL` чи `OK`. | Явне правило §1, §5 і §13. | Звіт має показувати кількість mismatch і конкретні ID/причини без вмісту файлів. |
| D-006 | Пробу виконувати лише безпечними read-only API/ADB-командами; непідтримувані або заборонені probes повертати як `UNAVAILABLE` із доказом/причиною. | Security §10 та етап 2 §5. | Немає root, `su`, reboot, запису чи зміни налаштувань у capability probe. |
| D-007 | Невідомі OEM quirks не є підставою відмовити в стандартному Android-механізмі; adapter додає evidence/quirk до capability, але не переносить дані. | §9 вимагає capability-only adapters і спільний транспорт. | Рішення про передачу лишається у спільному planner/provider коді. |
| D-008 | Приймати заяви про сумісність із фізичними телефонами лише після проходження відповідного device acceptance; локальні fixtures позначати як такі. | Samsung SM-G988B (Android 13/API 33) підключений; користувач дозволив root для ADB shell, `su -c id` повернув uid 0. | Фізичні acceptance можна виконувати поступово; один smoke test не є повним OEM/device acceptance. |
| D-009 | Усі приклади JSON у канонічному ТЗ мають проходити свої JSON Schemas; документацію очистити від зайвого Markdown escaping. | Перевірка знайшла розбіжності у manifest/report/receipt прикладах та відсутній receipt schema у переліку §4.2. | Приклади §5 і §7 оновлено та покрито regression test; у §4.2 додано `receipt.schema.json`. |
| D-010 | `receipt.json` — лише фінальний receipt; кожен повністю отриманий item класифікується рівно як verified або failed. | Транспортні ACK/checkpoint вже описують проміжний прогрес; неповний фінальний receipt може приховати тиху втрату. | Для кожної категорії вимагається `items_verified + items_failed == items_received`; проміжні стани не називаються receipt. |
| D-011 | Усі протокольні timestamps серіалізуються як UTC з літеральним суфіксом `Z`. | JSON Schemas обмежують поля `date-time` шаблоном `Z$`; Pydantic datetime serialization треба захистити тестом. | Додано wildcard field serializer, UTC formatter і тести для dynamic `datetime.now(timezone.utc)` model dumps. |
| D-012 | Google system accounts недоступні для стороннього APK; звітувати `UNAVAILABLE` з `OEM_RESTRICTION`. | Smart Switch користується OEM-підписаними системними привілеями, яких сторонній APK не має. | Показати повторний login/офіційний OEM transfer як дію користувача; не імітувати Smart Switch. |
| D-013 | Додати Space Preflight із batch-by-default, per-item streaming і Drop-Largest лише коли batch не вміщується; усі стратегії мають однакові SHA-256 та post-verification вимоги. | Batch із окремим staging та restore copy може вимагати близько `2 × total_size`; малий вільний обсяг не має блокувати перенесення, якщо streaming повністю вміщується. | Передача не стартує до перевірки volume-specific allocatable budget і потрібного user confirmation; автоматично не видаляються чужі дані. Streaming усередині item перезапускає лише цей item після обриву; cross-item checkpoints лишаються. Drop-Largest вибирає найбільшу за кількістю підмножину з `restore_sum + largest_staging_item <= safe_available`, а пропущені items записуються в report decisions/failures, не підроблений receipt. |
| D-014 | Android build toolchain = AGP 8.5.2 + Gradle 8.7 + Kotlin 2.0.20/Compose compiler plugin 2.0.20 + JDK 17; SDK targets залишаються compile/target 34, min 26. | AGP 8.5 підтримує API 34 і вимагає Gradle 8.7/JDK 17; Kotlin 2.0.20 підтримує AGP 8.5 і Gradle до 8.8. | Зафіксовану пару перевірено реальною `:app:assembleDebug`; локальний SDK шлях задається в ігнорованому `android-client/local.properties`. |
| D-015 | Android manifest декларує дозволи для MVP Tier A+B+D+E та окремо `READ_SMS`/`READ_CALL_LOG` для міграційного source export; Tier C write permissions не додавати до окремого рішення. Категорії просять runtime-дозволи після явного вибору. | Android scoped storage/SAF і Android 13–14 granular/partial media access обмежують широкі storage припущення; FGS на target API 34 потребує type-specific declaration; SMS/Call Log дозволи hard-restricted та залежать від installer grant і окремої Play declaration/approval. | Довільні документи/Downloads — через SAF; Wi-Fi scan/location та broad storage не потрібні. Відсутній SMS/Call Log grant дає `UNAVAILABLE/PERMISSION_DENIED`; sideload не гарантує grant. Не імітувати default SMS/Phone handler; cleartext network traffic вимкнено. |
| D-016 | Локальний sideload для розробки створюється зі стандартним debug signing і має стабільний шлях `android-client/dist/TransferKit-Android-debug.apk`; release key не генерується і не зберігається в репозиторії на цьому етапі. | Debug variant вже підписаний Gradle debug key, достатній для install/update на тестовому телефоні; постійний release signing key потребує окремого керування та резервування. | `build-sideload.bat` і `install-apk.bat` автоматизують dev artifact; production/release signing залишається у релізному наборі 082. |
| D-017 | Android `DeviceInfo` має contract identity fields (manufacturer, model, SDK, build fingerprint) і локальні diagnostics (Android release, RAM, внутрішній `/data` volume); у wire JSON можна передавати лише contract identity subset. | `manifest.schema.json` забороняє додаткові device properties; у той же час discovery/UI потребує release та resource metrics. | Не змінювати спільний контракт і не передавати resource metrics у manifest до окремого versioned рішення; серійні номери/IMEI не збирати. |
| D-018 | USB/ADB у базовому продукті означає Windows Station як ADB-хост; це не ADB-з’єднання телефон↔телефон. USB tethering/RNDIS/NCM лишається дослідницьким шляхом поза MVP; якщо він підтвердиться, використовує чинний TLS та Recovery handshake без нового TKXS frame. | Офіційна ADB-документація описує host-клієнт на development machine і RSA-довіру до нього; Android USB Host не гарантований кожному пристрою; запуск tethering з APK може вимагати системного `TETHER_PRIVILEGED`. | Для звичайного Android↔Android залишити Wi-Fi/точку доступу без ADB. Спершу перевірити кабель, USB-ролі/OTG, локальну IP-досяжність, системне вмикання tethering та виміряну швидкість на реальній парі; не обіцяти швидкість або авто-перемикання до доказу. |
| D-019 | Android contacts експортуються по одному агрегованому `Contacts` item у platform-generated vCard; джерельну sync-account identity не передавати. Target має використати свій обраний/default account або явно повідомлений local/device-only destination. | `Contacts` агрегує `RawContacts` з різних account sources; Android vCard API повертає provider-generated представлення, а виведення default/local account визначається цільовою системою. AOSP vCard default — 2.1, тому продукт не фіксує vCard 4.0. | До restore користувач має бачити destination account і можливість вибору; якщо destination не визначений — `USER_ACTION_REQUIRED`. Відсутність того самого Google/Samsung account на target не робить source capability `UNAVAILABLE`; local destination може не синхронізуватися. Unknown size має бути виміряний ManifestBuilder до schema item. |
| D-020 | Календар експортується по одному `CalendarContract.Events` row у canonical JSON v1 разом з attendee/reminder child rows; recurring event лишається master row. Source account/calendar identity та приватні extension data не є portable payload. | Android Calendar Provider моделює events, attendees, reminders, instances та extended properties окремими таблицями; повторювана подія відрізняється від похідних occurrences у `Instances`. `READ_CALENDAR` є небезпечним runtime-дозволом. | Запитувати `READ_CALENDAR` лише після явної дії. Source IDs потрібні лише для локальних запитів/hashed item ID; recurrence exception посилається на master лише через hashed item ID. Не експортувати sync account names/types; повідомляти `PARTIAL`, якщо provider вказує непереносні extended properties. На target користувач обирає destination calendar/account; restore лишається batch до idempotency/post-verify дизайну. Джерела: https://developer.android.com/reference/android/provider/CalendarContract, https://developer.android.com/reference/android/Manifest.permission#READ_CALENDAR. |
| D-021 | Tier C source export читає лише текстові SMS і call log після фактичного Android permission grant; не просити SMS/Phone default roles. MMS та Tier C restore лишаються поза реалізацією 039. | `READ_SMS` і `READ_CALL_LOG` — hard-restricted Android permissions. Google Play окремо перелічує backup/restore та cross-device transfer як use cases, на які можна подати policy exception, але схвалення не гарантоване; sideload сам по собі не знімає installer restriction. | Provider працює тільки з фактичним grant, не обходить його, не показує payload у UI/logs; недоступність звітується `PERMISSION_DENIED`, а не `NO_DATA`. Перед Tier C restore окремо перевірити write permissions, target handler, Play policy та provider semantics. Джерела: https://developer.android.com/reference/android/Manifest.permission#READ_SMS, https://developer.android.com/reference/android/Manifest.permission#READ_CALL_LOG, https://support.google.com/googleplay/android-developer/answer/10208820. |
| D-022 | APK export першої версії охоплює лише видимі, читабельні, single-file user-installed packages. System/updated-system і split packages не імпортуються в transferable set; їх кількості показуються користувачу. | `ApplicationInfo.sourceDir` надає шлях до base APK, тоді як split variants зберігаються окремими джерелами і мають встановлюватися як узгоджений пакетний набір; system package може залежати від platform signature/privileges. | `ApkProvider` не приховує пропуски, не передає source path і не називає видимість повнотою. Перевіряти package source SHA перед копіюванням; встановлення кожного item тільки після окремого підтвердження. Розширення split support потребує group-manifest та PackageInstaller multi-package acceptance. |
| D-023 | SettingsProvider v1 експортує лише явний read-only allowlist `Settings.System`; public API, Shizuku та Device Owner capability перевіряються як різні шляхи. | `Settings.System.canWrite()` вимагає окремого user special-access grant; Secure/Global і shell methods мають додаткові platform/OEM constraints, а Device Owner відкриває лише документовані policy API. | Не оголошувати універсальне читання/запис налаштувань і не змінювати settings під час probe. `WRITE_SECURE_SETTINGS` не додавати у звичайний manifest. Для кожного future write — окрема allowlist, user confirmation, policy-specific adapter і post-write readback. Джерела: https://developer.android.com/reference/android/provider/Settings.System, https://developer.android.com/reference/android/app/admin/DevicePolicyManager. |
| D-024 | `ManifestBuilder` фіксує вибраний category/item inventory, рахує per-item SHA-256 точних payload bytes і не підміняє невідомий size. Unknown-size item спершу стає приватним immutable cache snapshot; known-size source повторно перевіряється під час write-to-transport. | MediaStore/SAF/provider size hints можуть бути відсутні або змінитися; схема вимагає невід’ємний точний size та SHA-256, а immutable snapshot гарантує, що невідомий розмір і hash описують ті bytes, які підуть у передачу. | Build failure/permission denial фіксується окремо per item, така позиція не потрапляє у schema manifest; invalid contract abort-ить build. Snapshot directory видаляється через явний close/cancel lifecycle. Receiving Station усе одно застосовує JSON Schema. |
| D-025 | `shared/protocol-vectors.json` є єдиним джерелом golden byte vectors для Python і Android Kotlin codec-ів протоколу v1. | Ручні окремі приклади легко розходяться між мовами; повний frame hex перевіряє порядок байтів, UUID, ID hashes, CRC32, довжини та ACK поля разом. | Зміна wire layout вимагає protocol versioning і нових vectors; проходження fixture tests доводить лише сумісність codec-ів на описаних fixtures, не роботу receiver чи фізичного транспорту. |
| D-026 | Calendar child rows сортуються за унікальними полями attendee/reminder, не за неуточненим `_id`. | На Samsung Calendar Provider розгортає `Attendees` у join з `Events` та `Calendars`; `ORDER BY _id` спричиняв `SQLiteException: ambiguous column name: _id` і валив фонового worker-а. | Результати child rows стабільно canonicalize-яться за payload полями; `SQLException` додатково переводиться у UI category failure, а не в crash Activity. Перевірено на M31/API 31 після виправлення. |

| D-027 | Тримання екрана активним під час передачі є опційним і вимкненим за замовчуванням; воно діє лише для видимого Activity. `FLAG_KEEP_SCREEN_ON` і тимчасовий `screenBrightness` — window-only механізми; після opt-in початкова яскравість повзунка 15%, доступний діапазон 10–30%. Попередні атрибути вікна відновлюються після вимкнення опції/завершення/скасування. | Офіційний Android API утримує екран лише поки вікно видиме; у фоні екран гасне нормально. `screenBrightness` задає override 0..1 для вікна. Doze виникає за вимкненого екрана та обмежує мережу/CPU; Foreground Service підвищує пріоритет і показує повідомлення, але не є абсолютною гарантією проти системних/OEM обмежень. | Не змінювати system brightness, не просити `WRITE_SETTINGS`, не обіцяти запобігання OEM kill/Doze. Кнопка живлення може вимкнути дисплей; FGS, durable checkpoints і Recovery лишаються основним захистом. Пункт UI 049 перевіряє readability та відновлення попереднього window state на S20/M31. |
| D-028 | Android Receiver writes CRC-verified chunk bytes to app-private staging and `fsync`s them before committing SQLite checkpoint; each durable chunk checkpoint also stores payload SHA-256, so duplicate acceptance checks exact bytes beyond CRC32. A completed item is size/SHA-256 verified before moving into the app-private verified directory; final receipt is persisted only after every manifest item is classified. | The protocol requires ACK only after durable bytes plus checkpoint, retries may repeat ACK-lost chunks, and CRC32 alone can collide. Receiver item state and the final receipt need restart-safe, one-result-per-item accounting. | No incoming filename/path is trusted; internal storage names derive from transfer UUID and SHA-256 of category/item IDs. SHA mismatch remains a terminal `FAILED_INTEGRITY` receipt outcome. Receiver core is separate from socket/FGS wiring in checklist 048/051/054. |
| D-029 | Файловий restore v1 працює лише через app-owned MediaStore destinations на Android 10+ для photos/videos/audio/downloads; кожен item отримує deterministic marker з transfer/category/item IDs, пишеться як `IS_PENDING`, перевіряється за size/SHA-256 при записі та повторним читанням, і лише тоді публікується. | MediaStore destination може лишитися після process death до збереження receipt; детерміноване ім’я дозволяє знайти власний рядок, перевірити його й уникнути дубліката без overwrite чужого файла. Android 8–9 потребує окремого legacy API/permission adapter; documents потребують user-selected SAF destination. | Невідповідний існуючий marker не перезаписувати й не видаляти; повертати per-item failure. `RESTORED` можливий тільки після destination post-verification. Contacts/Calendar/SMS/APK/Settings лишаються unavailable до окремих adapter-ів. Реалізація додана, але build/API behavior ще не перевірені. |
| D-030 | Android build використовує один узгоджений JDK 17, SDK 34, Build Tools 34.0.0 і Gradle Wrapper 8.7; ADB-команди адресуються через SDK `platform-tools` та serial. | На цій машині були конфлікт системного Gradle/native library, різні ADB клієнти та два одночасно підключені телефони; ці помилки часто виглядають як помилка коду, хоча є проблемою середовища/target selection. | Додано opt-in read-only `android-client/doctor.ps1` і troubleshooting guide; поки не вбудовувати неперевірений doctor у працюючий `build-sideload.bat`. `-Devices` окремо opt-in і запускає ADB server/listing. `adb-shell` прибрано з Python requirements, бо source code використовує ADB executable й не імпортує цю бібліотеку. Не називати preflight доказом compilation/test/device acceptance; новий шлях ще не запускали. |
| D-033 | Неперевірений developer preflight запускається вручну і не має блокувати наявний sideload build, доки його поведінку не перевірено. | PowerShell SDK/JDK parsing має кілька platform-specific шляхів і локальний build раніше вже працював; додавання невиконаного preflight як обов’язкового кроку могло б заблокувати користувачеві збірку без помилки у source. | Run `doctor.ps1 -BuildOnly` окремо перед build, коли це потрібно; інтеграцію в `build-sideload.bat` розглядати після перевірки false positive/negative. Ця гілка лишається без тестів/build. |
| D-034 | APK restore починається з одного explicitly confirmed `PackageInstaller.Session`; caller не може вважати його успішним до callback `STATUS_SUCCESS` і package/version readback. | `PackageInstaller` є асинхронним і може показати власний системний confirmation UI; source file hash сам не доводить, що target дійсно встановив item. | `ApkInstallCoordinator` stream-ить bytes у session, fsync-ить, reread-хешує й чекає caller status receiver.
